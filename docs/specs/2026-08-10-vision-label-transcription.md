# 이미지 라벨 전사 (비전 제안 → 사람 진술)

한국 브랜드는 등록성분량을 텍스트가 아니라 상세페이지 이미지로 싣는다.
텍스트 수집 파이프라인은 그 앞에서 끝나고, 그렇게 막힌 것이 국내 스켈레톤 102건이다 — 지금 남은 작업 중 가장 큰 덩어리다.
이 설계는 그 벽을 자동화로 뚫지 않는다. **기계가 전사안을 만들고 사람이 그것을 진술한다.**

## 왜 자동화로 끝낼 수 없는가

파이프라인의 신뢰 경계는 하나다: 값은 보관 원문에 문자 그대로 있는 구절로만 뒷받침된다.
이미지에는 원문이 없다.
비전 모델의 출력을 `captured_text`로 저장하면 그 다음 구절 검사는 **모델이 쓴 글을 모델이 대조하는 순환**이 되어, 환각을 막으려고 만든 가드가 환각을 통과시키는 장치로 바뀐다.

그래서 경계를 사람으로 옮긴다.
`captureMethod: "manual"`이 원래 뜻하는 것이 정확히 그것이고 — 사람이 라벨을 읽고 옮겨 적었다는 진술 — 2026-08-10부터 그 등록은 사람 세션만 할 수 있다.
이 설계는 그 제약을 우회하지 않고 그것에 맞춰 세운다.

## 범위

대상은 라벨이 이미지로만 존재하는 사료다.

- 국내 브랜드 스켈레톤 102건 (주 대상)
- 남은 탄수 공백 61건 중 국내 브랜드 4건 (ANF 3, 퓨어네이쳐 1)

제외: 홈페이지가 없는 국내 브랜드 14개. 이미지에 도달할 경로 자체가 없으므로 대상이 아니며, 목록으로 보고한다.

Pet Friends는 경로가 아니다. 상품 페이지가 브라우저 User-Agent 로도 403을 돌려주며(확인 2026-08-10), 서버에서 도달할 수 없다.
브랜드 자체 사이트는 열린다(캐츠랑·더리얼·풀무원·이즈칸 모두 200).

## 흐름

```plaintext
1  scripts/transcribe-brand.mjs --brand <이름> [--limit N] [--dry]
   ├ 브랜드 homepage_url + 그 브랜드의 스켈레톤 목록을 읽는다
   ├ codex ① : 제품 페이지 URL + 등록성분량이 보이는 상세 이미지 URL 을 사료별로
   ├ 서버가 이미지를 내려받는다 — content-type image/*, 크기 상한, 해시
   ├ codex ② : -i <파일들> 로 등록성분량 블록을 그대로 전사
   └ POST /api/research/transcripts → food_research_runs (status='pending_review')
      ※ 출처도 값도 쓰지 않는다

2  /new/transcribe  (운영자 세션)
   ├ pending_review 를 이미지 옆에 전사안·파싱값과 나란히 표시
   ├ [승인] POST /api/foods/:id/sources (manual) → /sources/apply
   ├ [수정] 고친 텍스트로 같은 경로
   └ [건너뜀] run 을 rejected 로
```

승인·수정·건너뜀은 모두 브라우저의 운영자 세션에서 나간다.
스크립트는 제안까지만 하고 값에 손대지 않는다.

## 적재 위치

새 표를 만들지 않고 `food_research_runs` 에 `pending_review` 상태를 추가한다.

그 표는 이미 `food_id + agent_name/model + proposal(jsonb) + captures(jsonb) + status` 를 갖고 있고, 이 기능이 필요한 것과 같은 모양이다.
상태값 하나를 위해 표·RLS·리포지토리를 새로 만드는 것은 이 프로젝트가 줄여 온 종류의 무게다.

- `proposal` — 전사본과 파싱된 값·구절
- `captures` — 제품 페이지 URL, 이미지 URL, 이미지 해시
- `status` — `pending_review` → 승인 시 `applied`, 건너뜀 시 `rejected`

되돌리기 쉬운 결정이다. 원장의 의미가 흐려진다고 판단되면 표를 분리한다.

## 신뢰 경계

| 단계        | 무엇이 보증하는가                                                      |
| ----------- | ---------------------------------------------------------------------- |
| 이미지 수집 | content-type 과 크기를 서버가 확인한다. 텍스트 수집과 같은 가드        |
| 전사        | **아무것도 보증하지 않는다.** 기계 출력이며 제안일 뿐이다              |
| 승인        | 사람이 이미지와 전사안을 나란히 보고 진술한다. `manual` 이 뜻하는 그것 |
| 근거 적용   | 구절이 승인된 텍스트에 문자 그대로 있는지 검사한다                     |

마지막 줄이 중요하다.
사람이 전사안을 수정하다 구절과 값이 어긋나면 근거 적용이 거절한다 — 사람의 실수를 잡는 자리가 남는다.

## 실패 처리

| 상황                                      | 결과                                                          |
| ----------------------------------------- | ------------------------------------------------------------- |
| 이미지 수집 실패 / image 아님 / 크기 초과 | run `capture_failed`, 사료는 스켈레톤으로 남음                |
| codex 가 성분표를 못 찾음                 | run `rejected`. 재시도 신호가 아니다                          |
| 브랜드에 homepage_url 없음                | 대상 아님. 실행 시작 시 목록으로 보고                         |
| 운영자가 건너뜀                           | run `rejected`. 같은 사료가 다음 실행에서 다시 제안될 수 있다 |

국내 브랜드의 빈 결과 세 형태(URL 없음 / 제안 없음 / 거절)가 모두 종료라는 기존 판단은 그대로다.
이 설계는 그 판단을 뒤집는 게 아니라, **텍스트가 아니라 이미지를 읽는 경로를 하나 더 여는 것**이다.

## 만들지 않는 것

- 이미지 저장소 — URL 과 해시만 남기고 필요하면 다시 내려받는다
- OCR 폴백 — 비전 모델이 못 읽으면 사람이 읽는다
- 화면에서의 붙여넣기·업로드 경로 — 브랜드 사이트 경로 하나로 간다
- 화면에서의 온디맨드 비전 호출 — 배치로 미리 쌓고 사람은 검토만 한다

## 검증

- 전사 엔드포인트가 값을 쓰지 못한다는 경계 테스트 (제안만 적재)
- 이미지 수집 가드 단위 테스트 (content-type, 크기 상한)
- 승인이 사람 세션을 요구한다는 것은 `src/app/api/foods/[id]/sources/route.test.ts` 가 이미 고정하고 있다

## 순서

codex ① 은 수입 브랜드에서 겪은 것과 같은 발견 문제다.
국내 사이트는 열리지만 제품 페이지 구조는 브랜드마다 다르므로 한 번에 다 될 것으로 보지 않는다.

큰 브랜드 하나(캐츠랑 9건 또는 더리얼 7건)로 먼저 돌려 성공률을 보고, 그 결과로 나머지에 붙일지 판단한다.
